作品概述

步衡 WalkScope 面向自然资源和规划相关业务人员、规划设计团队及城市更新研究者，将公共服务设施检索、实际步行服务范围分析和报告编写整合到同一工作流程。用户指定中心点后，可以查看七组设施及45个小项的分布与服务缺口，并通过一个对话框提出问题、调整研判文字、导出可编辑 Word。

平台把空间计算结果与模型文字处理分开：地图、设施数量和覆盖比例来自保存的测算结果，模型据此解释问题和改写报告。当前同济案例的设施配置参考分为55，用户可进一步按大类和小类查看差异，将地图发现转为后续调查任务。

01  项目背景


## 01  项目背景

规划前期排查需要连续的证据链

公共服务设施研究通常同时面对三类问题：周边有哪些设施、这些设施能够服务到哪些位置，以及如何把地图发现整理成可讨论的研判意见。设施数量、服务覆盖和报告表达分别回答不同问题，工作中需要把它们放在同一分析范围内理解。

单看点位数量，难以识别河流、封闭边界或出入口等步行条件带来的差异；只看大类整体覆盖，又容易忽略托育、助餐等具体小项的缺口。报告编写还需要反复核对名称、比例和分析口径，避免文字与地图使用不同结果。

本项目解决的具体问题

步衡以指定中心点的步行生活圈为共同分析对象，将设施检索、路径与服务区、大小类缺口和报告草稿连接起来。用户可以沿着“发现点位—理解服务范围—定位待核查问题—形成文字成果”的顺序工作，减少在地图截图、数据表格和文档之间来回整理。

平台服务于详细规划、城市更新和设施布局研究的前期排查。它提供可复核的地图线索和文字初稿；进入正式方案论证时，仍需结合人口需求、设施容量、开放条件和现场调查判断服务是否真正充足。

分析对象与输出

分析对象是用户指定中心周边的步行圈。主要输出包括设施清单、分组与小类结果、服务覆盖和盲区、设施配置参考分，以及可在对话中修改并导出的研判报告。行政社区边界和人口服务对象可在后续调查中进一步衔接。

02  应用场景与使用流程


## 02  应用场景与使用流程

| 使用场景 | 如何使用成果 |
| --- | --- |
| 详细规划前期调研 | 按教育、医疗、养老等组别检查设施分布，梳理需要联系部门或运营方核实的清单 |
| 城市更新基础排查 | 在更新片区选定代表中心，查看周边步行联系及具体服务小项的缺口，辅助安排调查重点 |
| 公共服务设施专题研究 | 将大类与小类结果对照，识别“整体有服务、具体功能仍不足”的情况，继续补充容量和开放条件 |
| 内部汇报与方案讨论 | 围绕地图结果提问，按讨论重点调整报告文字，导出Word继续编辑、批注和沟通 |
从地点到报告的操作流程

01  选择地点与分析类别

输入城市、街道或具体地点并选择地址建议，再选择需要分析的设施组。演示时也可直接载入同济保存案例，重复查看同一份结果。

02  查看地图与设施

浏览七组设施卡片，按大类或小类筛选点位；点击设施查看路线，再通过图层窗口检查服务覆盖与浅蓝缺口。

03  围绕结果提问和修改

打开报告对话，先阅读完整初稿。可以询问分析结果，也可以直接输入“把第四章写得更具体一些”或“把第三章去掉”等修改要求。

04  导出并继续讨论

每份报告卡片下提供Word导出，文件内容对应卡片中的报告。关闭再打开对话保留本页修改，刷新后重新回到完整初稿。

03  技术架构


## 03  技术架构

系统由浏览器前端、FastAPI 服务端、空间测算模块和独立报告草稿模块组成。Vue 3与Vite负责界面和交互，Shapely与NumPy承担几何与数值处理，百度地图提供底图、地点及步行服务，DeepSeek API负责问答和研判文字改写。

| 组成 | 主要职责 |
| --- | --- |
| 前端展示层 | 地址选择、任务进度、地图点位与图层、七组评分卡、统一报告对话、Word下载 |
| API与任务层 | 接收地点与体检请求，组织检索和测算流程，读取保存结果，提供问答及草稿接口 |
| 空间分析层 | 处理真实POI、实际步行测距、中心步行圈、设施服务区、覆盖和盲区，以及数量参考评分 |
| 报告处理层 | 提取锁定事实，生成完整章节，校验模型返回的修改，保存页面草稿并导出Word |
| 存储与复现层 | 保存原始报告、完整初稿、页面修改及卡片快照；通过样例摘要和测试复核输入与输出 |
数据如何流转

中心点与类别选择 → 设施检索 → 步行测距与服务区计算 → 保存测算报告 → 地图展示与事实提取 → 对话解释或修改 → Word导出。报告文字修改读取已有结果，不重新触发设施检索和测距。

服务与配置的分工

浏览器地图AK用于加载地图SDK；服务端百度AK用于实际地点及路径请求；DeepSeek Key仅供服务端模型通道使用。保存案例可以回放已完成测算，未配置模型服务时仍能读取事实稿和导出Word。

源码按app、frontend、contracts、tests、tools和docs等职责组织，提供依赖锁文件、样例还原工具、运行说明和自动验证流程，便于审阅与复现。

04  空间分析与地图表达


## 04  空间分析与地图表达

托育小类服务分析：覆盖19.05%，确认盲区80.95%，未知显示0.00%。

![托育小类服务分析：覆盖19.05%，确认盲区80.95%，未知显示0.00%。](assets/02_托育小类浅蓝缺口.png)

以步行服务范围连接设施与空间

中心15分钟步行圈采用100米采样；设施服务区从真实POI位置出发，结合实际步行测距构建1000米等距线，边界通过采样插值形成。20米网格用于覆盖分析辅助，最终地图表达采用连续服务区与统一点阵。

圈内设施参与数量参考评分；圈外邻近设施也可能向圈内提供服务，因此覆盖计算保留圈外候选的作用。数量参考分与覆盖比例分别展示，帮助用户区分“设施有多少”和“服务到哪里”。

大类、小类与信息缺口分别解释

大类共同盲区表示该组所有小项均未提供服务的部分；小类图层读取自身保存几何。确认盲区和未知区域统一用浅蓝高亮，数据中仍区分“已有证据判定未覆盖”和“证据尚不充分”。同济45小项未知比例均小于1e-8，界面显示0.00%，对应本轮采样估算完成。

05  报告问答、修改与导出


## 05  报告问答、修改与导出

统一报告对话：完整初稿、一个输入框、报告卡片下的Word导出。

![统一报告对话：完整初稿、一个输入框、报告卡片下的Word导出。](assets/03_统一对话与Word导出.png)

报告初稿包含分析对象与用途、测算口径、设施现状与服务缺口、规划研判与后续调研建议、依据与适用边界，以及设施小项结果附表。用户在同一输入框中提出问题或修改要求，避免先切换多种操作模式。

模型处理的是第三至第五章的研判正文。服务端将报告编号、来源摘要和测算事实锁定，并校验结构化修改结果；设施数量、参考分、覆盖比例和原始几何保持与保存报告一致。

输入“把第三章去掉”后，本页报告及其Word导出同步删除该章；刷新后恢复完整初稿。真实模型联调也已验证强化养老与助残专项调研的段落改写，导出内容与修改后的草稿一致。

页面、报告卡片和Word对应同一份草稿快照，便于连续讨论和追溯修改。当前文字编辑范围为章节正文、删除与恢复；Word导出后可继续在文档软件中调整版式。

06  创新点


## 06  创新点

01  把实际步行服务分析接入报告工作流

平台将设施点位、步行路线、服务区与报告文字放在同一条流程中。用户从地图发现问题后，可以直接围绕保存结果提问并形成报告，减少重新整理截图和抄录指标的步骤。

02  大类与小类独立核对，保留差异

七组整体结果帮助快速浏览，45个小项支持进一步定位具体功能缺口。每个小类使用自己的测算几何，避免整体覆盖较高时掩盖某一服务功能不足，也避免用父级结果代替尚未完成的小类分析。

03  事实与文字分离的模型协作

模型参与结果解释和研判表达，测算事实由独立数据结构提供。服务端检查来源、锁定字段和可编辑章节，再保存修改，使自然语言交互与数值、附表的一致性能够同时得到验证。

04  将交互式报告变成可交接的成果

一个对话框承接提问与修改，报告卡片提供对应Word，页面刷新恢复完整初稿。保存案例、文件摘要、回归测试及自动验证共同支持重复演示和成果交接。

创新点的适用范围

以上创新点体现本项目在工作流与工程实现上的设计特点。设施服务判断采用采样估算，后续研究可结合开放条件、容量与人口需求，进一步检验空间结果在规划任务中的适用性。

工程与交互验证

本机源码副本及GitHub Ubuntu全新环境均通过依赖安装、样例还原、后端825项与前端236项测试、类型检查、生产构建和离线自检。3项需要外部百度服务的测试默认跳过。实际页面与Word已核对删章、连续修改和刷新恢复行为。

成果交付

项目提供可运行源码、完整保存案例、作品介绍、技术设计、验收说明及完整初稿Word。代码保留原MIT许可与署名，依赖和第三方地图数据另列来源说明。仓库中的大样例以带摘要的压缩包保存，还原后恢复原路径和原始字节。

后续建设

后续将围绕设施开放时段、服务容量与人口需求补充核查，扩大不同地区案例验证，并完善多人使用时的权限、持久化和运行监控。
