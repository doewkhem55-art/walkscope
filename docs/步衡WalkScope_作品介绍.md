# 步衡 WalkScope 作品介绍

步衡 WalkScope

15分钟生活圈公共服务设施体检与规划研判平台

刘彦和  于明睿    野蛮人鲈鱼豪

摘要  步衡 WalkScope面向详细规划、城市更新和公共服务设施研究的前期排查，将设施检索、实际步行服务分析与报告编写整合为一条连续工作流程。系统以指定中心点的步行生活圈为分析对象，支持七组设施、45个小项的点位与路线查看、服务覆盖及大小类盲区分析，并通过统一对话完成结果提问、研判文字修改与Word导出。平台采用Vue与FastAPI组织交互和任务，利用空间处理模块生成保存测算结果，再以锁定事实约束模型改写。同济大学四平路校区周边案例的设施配置参考分为55；本机及Ubuntu全新环境已通过回归、构建和离线自检。成果可用于形成设施调查线索、专题核查清单与可编辑的研判初稿。

关键词  15分钟生活圈；公共服务设施；步行可达性；空间分析；报告生成


## 1 项目背景


### 1.1 业务问题与建设目标

公共服务设施研究需要同时回答周边有哪些设施、设施能够服务到哪些位置，以及如何将地图发现整理为可讨论的规划意见。数量统计、服务范围和报告表达分别对应不同问题，使用时需要保持共同的分析对象和一致的数据来源。

单看点位数量，难以识别河流、封闭边界及出入口等步行条件造成的差异；只看某一大类的整体覆盖，又容易忽略托育、助餐等具体功能的缺口。编写报告时还需要反复核对名称、数量和比例，确保正文与地图引用的是同一份结果。

步衡以指定中心点的步行生活圈连接设施检索、路径与服务区、大小类缺口和报告草稿。用户可沿着发现点位、理解服务范围、定位待核查问题和形成文字成果的顺序工作，减少在地图截图、数据表格和文档之间重复整理。


### 1.2 分析对象与成果定位

平台面向自然资源和规划相关业务人员、规划设计团队及城市更新研究者，提供设施清单、地图证据、参考指标和研判初稿。分析域是指定中心周边的步行圈，后续可与行政社区边界、人口服务对象及设施台账衔接。正式方案论证仍需结合开放条件、容量、人口需求和现场调查判断服务是否充足。


## 2 应用场景与业务流程


### 2.1 主要应用场景

在详细规划前期调研中，业务人员可以按教育、医疗、养老等组别浏览设施分布，再逐项检查具体功能，形成需要联系部门或运营方核实的清单。在城市更新基础排查中，可以从片区内代表地点出发，查看步行联系与服务缺口，将地图发现转化为调查重点。

在公共服务设施专题研究中，大类与小类结果可以相互对照，识别整体已有服务但具体功能仍不足的情况，再补充开放时段、容量与服务对象资料。在内部汇报和方案讨论中，用户可围绕保存结果提问，按讨论重点调整报告文字，并导出Word继续编辑和批注。


### 2.2 从地点到报告的操作流程

首先，输入城市、街道或具体地点并选择地址建议，再选择分析类别；演示和重复核对时可直接载入同济保存案例。随后，通过七组设施卡片筛选大类或小类，点击设施查看路线，并在图层窗口检查服务范围和浅蓝缺口。

地图查看完成后，打开报告对话阅读完整初稿，在同一输入框中提出问题或直接输入修改要求。例如，“把第四章写得更具体一些”用于调整研判正文，“把第三章去掉”用于删除指定章节。每份报告卡片下提供Word导出，导出内容与该卡片对应。关闭再打开对话保留本页修改，刷新后恢复完整初稿。


## 3 技术架构与空间分析


### 3.1 系统组成

系统由浏览器前端、FastAPI服务端、空间分析模块与独立报告模块组成。Vue 3和Vite承担界面与交互，Shapely和NumPy处理几何及数值运算，百度地图提供底图、地点和步行服务，DeepSeek API参与问答和研判文字改写。各部分职责见表1。

表1 系统组成与主要职责

| 组成 | 主要职责 |
| --- | --- |
| 前端展示 | 地址选择、任务进度、点位和路线、图层、七组卡片、报告对话与Word下载 |
| API与任务 | 接收地点和体检请求，组织检索与测算，读取保存结果，提供问答及草稿接口 |
| 空间分析 | 处理真实POI、步行测距、中心步行圈、设施服务区、覆盖和盲区、数量参考评分 |
| 报告处理 | 提取锁定事实，生成完整章节，校验模型修改，保存页面草稿并导出Word |
| 存储与复现 | 保存测算报告、完整初稿和卡片快照，以摘要和固定样例支持复核 |
数据按中心点与类别选择、设施检索、步行测距与服务区计算、保存测算报告、地图展示与事实提取、对话解释或修改、Word导出的顺序流转。地图和报告共用保存结果，文字修改读取已有事实，不重新触发设施检索和测距。


### 3.2 中心步行圈与设施服务区

中心15分钟步行圈采用100米采样；设施服务区从真实POI位置出发，以1000米实际步行距离为阈值，结合测距采样与插值形成连续边界。20米网格用于覆盖分析辅助，最终地图表达采用连续服务范围与统一点距的点阵。

圈内设施用于数量参考评分；圈外邻近设施也可能向圈内提供服务，因此覆盖计算保留圈外候选的作用。设施配置参考分按圈内数量分档，覆盖比例根据服务区几何计算，分别反映设施数量配置与服务范围，不能相互替代。


### 3.3 大小类结果与未知区域

大类共同盲区采用组内小项服务区的组合结果。该组只要有任意小项提供服务，相应位置便不属于共同盲区。小类图层只使用自身保存几何，缺少小类证据时给出缺失状态，不从父级复制结果。

确认盲区与未知区域分别保留：前者对应已有证据支持的未覆盖部分，后者对应证据不足或尚未充分核验的部分。两者可统一使用浅蓝高亮，但数据与文字仍保留不同含义。同济45小项的未知比例均小于1e-8，界面显示0.00%，对应本轮采样估算完成。


### 3.4 事实数据与模型文字分工

原始报告记录中心、结果时间、分组、小类、POI、步行和覆盖几何。报告模块从中提取锁定事实，将参考分、设施数量、覆盖比例及原始几何与可编辑文字分开保存。模型用于解释结果和改写研判正文，服务端校验允许章节及结构化返回结果后，再更新草稿。

读取和导出前核对报告编号、来源摘要与事实一致性；校验失败时保留当前稿。该机制使自然语言修改可以进入报告流程，同时保持地图、附表和文字引用的测算事实一致。


## 4 核心功能与交互实现


### 4.1 地图浏览与服务缺口检查

七组设施卡片提供总体浏览入口，图层窗口支持进一步查看45个小项。用户可切换设施点、时间档点阵、大小类盲区和圈外候选，并点击点位查看路线。托育小类的实际界面如图1所示。


![图1 托育小类的服务覆盖与浅蓝缺口](assets/02_托育小类浅蓝缺口.png)

图中托育覆盖19.05%、确认盲区80.95%、未知显示0.00%。用户可从空间分布判断下一步调查的重点，再核查地图点位是否真实、校园内部设施是否对外开放，以及实际服务时段、容量和对象。


### 4.2 统一报告对话

报告初稿包含分析对象与用途、测算口径、设施现状与服务缺口、规划研判与后续调研建议、依据与适用边界，以及设施小项结果附表。一个输入框承接结果提问和文字修改，每份报告下提供对应Word导出，界面如图2所示。


![图2 统一报告对话与Word导出](assets/03_统一对话与Word导出.png)

当前文字编辑范围为第三至第五章正文的改写、删除和恢复；固定分析范围、测算方法与数据附表受到保护。输入“把第三章去掉”后，本页报告及对应Word同步删除该章。真实模型联调也已验证强化养老与助残专项调研的段落改写，导出内容与新稿一致。


### 4.3 页面草稿与卡片快照

页面初始化生成UUID，读取、修改和导出传递同一ID；关闭对话窗口时ID保持不变。新页面从独立baselines读取完整初稿，缺少基线时构建完整事实稿，不继承历史删章测试内容。

修改结果写入本页sessions，内部一致性号用于识别并发和过期请求。报告卡片保存对应快照，继续修改后仍可导出早先卡片的内容。刷新生成新页面ID并恢复完整初稿，界面、文件名与Word正文均不显示内部修订编号。服务端校验UUID，拒绝路径式非法ID。

草稿接口包括读取GET /api/v1/checkups/{id}/draft、流式修改POST /api/v1/checkups/{id}/draft/stream和Word导出POST /api/v1/checkups/{id}/draft/export。请求携带页面身份与内部一致性号，服务端据此定位会话并校验当前草稿。


## 5 创新点


### 5.1 实际步行服务分析与报告工作流衔接

平台将设施点位、步行路线、服务区和报告文字置于同一条流程中。用户可直接围绕地图中发现的问题提问，依据保存结果形成报告，减少重新整理截图和抄录指标的步骤，使空间证据更容易进入后续调研和沟通。


### 5.2 大类与小类独立核对

七组整体结果帮助快速浏览，45个小项支持定位具体功能。每个小类使用自身测算几何，避免整体覆盖较高时掩盖某一功能不足，也避免用父级结果代替尚未完成的小类分析。信息缺口在数据中单独保留，便于区分需要补算与需要实地核实的问题。


### 5.3 受事实约束的模型协作

模型参与结果解释和研判表达，测算事实由独立结构提供。来源、锁定字段、允许章节及导出一致性在服务端校验，使自然语言交互与数值、附表的一致性可以同时被验证。


### 5.4 从交互草稿到可交接成果

统一对话、卡片快照、Word导出和刷新恢复完整初稿共同支持连续讨论与重复演示。保存案例、文件摘要、回归测试和自动验证进一步将界面操作转化为可复核、可交接的工程成果。


## 6 案例成果与验证


### 6.1 同济案例结果

同济大学四平路校区周边保存案例包含7大类45小项，设施配置参考分55。点位卡片、路线、小类盲区与报告使用同一保存结果，部分小类指标见表2。圈内检索数量与覆盖比例具有不同口径，圈外设施也可能提供圈内覆盖。

表2 部分设施小类的保存结果

| 设施小类 | 覆盖 | 确认盲区 | 未知 |
| --- | --- | --- | --- |
| 小学 | 99.81% | 0.19% | 0.00% |
| 药店 | 96.67% | 3.33% | 0.00% |
| 菜市场 | 93.60% | 6.40% | 0.00% |
| 婴幼儿托育 | 19.05% | 80.95% | 0.00% |
小学、药店与菜市场在保存结果中覆盖相对较高，托育小类则存在更大未覆盖部分。这些结果用于安排后续核查优先顺序；覆盖估算尚需与设施开放条件、容量及人口需求结合，不能直接作为法定规划达标结论。

### 6.3 操作验收与一致性核对

实际页面核对包括：载入保存案例后显示七组45小项与参考分55；选择托育后读取自身几何并显示相应比例；打开报告时默认包含第三章；输入删章指令后才修改本页报告，Word同步删除；关闭重开保留修改，刷新后恢复完整初稿。

API和前端回归还核对页面UUID在读取、修改和导出时保持一致，以及旧卡片快照导出、非法页ID拒绝和锁定事实一致等行为。上述测试验证代码契约和操作结果，设施分类准确率、空间插值误差、容量及现场可用性还需专项评估。


## 7 部署与复现


### 7.1 运行环境与样例还原

环境采用Python 3.12与Node.js 24。后端依赖由requirements.lock.txt锁定，前端由package-lock.json锁定。仓库较大保存输入以data/offline-samples.zip归档，配套索引列明52项文件的路径、大小和SHA-256摘要。

克隆后先运行python tools/unpack_offline_samples.py。脚本核验归档及每个文件的摘要，恢复原始路径；如果已有文件与样例不同则拒绝覆盖。重复执行时只验证已存在的相同文件，便于稳定复现。

表4 安装与运行步骤

| 步骤 | 操作 |
| --- | --- |
| 还原样例 | python tools/unpack_offline_samples.py |
| 安装后端 | python -m venv .venv；激活后运行python -m pip install -r requirements.lock.txt |
| 安装前端 | 进入frontend目录运行npm ci |
| 配置服务 | 复制.env.example为.env，frontend/.env.example为frontend/.env.local，再按需要填写本机配置 |
| 启动后端 | python tools/dev.py backend |
| 启动前端 | python tools/dev.py frontend |
| 回归验证 | python -m pytest -q；前端运行npm test、npm run build |
| 样例自检 | python tools/verify_handoff.py |

### 7.2 服务配置与访问

后端默认使用8768端口，前端默认使用5173端口。打开前端后可载入同济保存案例；也可通过view=map、report=tongji-all7-small-updated-20261027及base参数指定案例与后端地址。

浏览器百度AK用于加载地图SDK，服务端百度AK用于新的地点与步行请求，DeepSeek Key只用于服务端模型通道。未配置模型服务时，保存事实稿和Word导出仍可使用；自由文字改写需要有效模型配置，模型不可用时明确提示。精确删章等本地操作可独立完成。


### 7.3 存储与部署边界

原始测算报告、完整初稿、页面会话和卡片快照分开存储。当前原型使用本地文件和单进程方式；多人部署需要补充鉴权、事务持久化、配额和审计。保存报告可以持续读取，运行或暂停任务的执行栈在进程重启后不能直接延续。
